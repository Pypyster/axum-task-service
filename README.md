# Axum Task Service

REST API для управления задачами, написанный на Rust с использованием
[Axum](https://github.com/tokio-rs/axum) и PostgreSQL.

Проект построен по слоистой архитектуре: HTTP-обработчики не обращаются к базе
данных напрямую. Запрос проходит через сервисный слой, где располагается
бизнес-логика, затем через репозитории, отвечающие за доступ к данным, и только
после этого попадает в PostgreSQL.

> Проект находится в разработке. API, структура базы данных и набор endpoint'ов
> могут дополняться и изменяться.

## Возможности

- Создание, получение, обновление и удаление задач
- Работа с пользователями
- Хранение данных в PostgreSQL
- Асинхронная обработка HTTP-запросов
- Разделение HTTP-слоя, бизнес-логики и слоя доступа к данным
- Централизованная обработка ошибок
- Основа для масштабирования, тестирования и расширения API

## Архитектура

Проект использует слоистую архитектуру. Каждый слой отвечает только за свою
область работы и не смешивает HTTP-логику, бизнес-правила и SQL-запросы.

```text
Client
  │
  ▼
HTTP Handlers
  │
  ▼
Service Layer
  │
  ▼
Repository Layer
  │
  ▼
PostgreSQL Database
```

### Назначение слоёв

| Слой | Каталог | Ответственность |
|---|---|---|
| Точка входа | `src/main.rs` | Инициализация приложения, настройка роутера, зависимостей и HTTP-сервера |
| HTTP Handlers | `src/heandlers/` | Приём HTTP-запросов, извлечение данных, вызов сервисов и формирование HTTP-ответов |
| Service Layer | `src/service/` | Бизнес-логика приложения и правила работы с задачами и пользователями |
| Repository Layer | `src/repository/` | Изолированный доступ к PostgreSQL и выполнение запросов к данным |
| Database Models | `src/db/` | Модели и структуры данных, связанные с пользователями и задачами |
| Errors | `src/errors/` | Ошибки приложения и преобразование ошибок в корректные HTTP-ответы |
| Database | PostgreSQL | Постоянное хранение данных приложения |

### Поток обработки запроса

Например, создание задачи проходит через приложение следующим образом:

```text
POST /tasks
  │
  ▼
Task Handler получает JSON-запрос
  │
  ▼
Task Service проверяет бизнес-правила
  │
  ▼
Task Repository сохраняет данные в PostgreSQL
  │
  ▼
Handler возвращает HTTP 201 Created
```

Такое разделение делает проект понятнее, упрощает тестирование и позволяет
изменять SQL-запросы или HTTP-слой без переписывания всей бизнес-логики.

## База данных

Для хранения данных используется **PostgreSQL** — реляционная база данных,
подходящая для работы с пользователями, задачами, статусами и связями между
сущностями.

Доступ к PostgreSQL должен выполняться только через слой `repository`.
Благодаря этому HTTP-обработчики и сервисы не зависят от конкретных SQL-запросов,
схемы таблиц или деталей подключения к базе данных.

```text
Handler → Service → Repository → PostgreSQL
```

Для подключения к базе данных используется переменная окружения `DATABASE_URL`.

Пример `.env.example`:

```env
DATABASE_URL=postgres://USERNAME:PASSWORD@localhost:5432/axum_task_service
```

## Быстрый старт

### Требования

Перед запуском должны быть установлены:

- [Rust](https://www.rust-lang.org/tools/install) и Cargo
- Git
- PostgreSQL 14+ или более новая версия

Проверьте установку Rust:

```bash
rustc --version
cargo --version
```

### Клонирование проекта

```bash
git clone [https://github.com/Pypyster/axum-task-service.git](https://github.com/Pypyster/axum-task-service.git)
cd axum-task-service/axum-task-service
```

### Настройка PostgreSQL

Создайте базу данных:

```sql
CREATE DATABASE axum_task_service;
```

Создайте файл `.env` в корне Rust-проекта рядом с `Cargo.toml`:

```env
DATABASE_URL=postgres://postgres:password@localhost:5432/axum_task_service
```

### Сборка и проверка

Проверить проект без создания исполняемого файла:

```bash
cargo check
```

Запустить тесты:

```bash
cargo test
```

Отформатировать код:

```bash
cargo fmt
```

Проверить форматирование без изменения файлов:

```bash
cargo fmt --check
```

Запустить статический анализ:

```bash
cargo clippy -- -D warnings
```

### Запуск приложения

```bash
cargo run
```

После запуска сервер будет доступен по адресу и порту, указанным в конфигурации
приложения или в `src/main.rs`.

## Пример API

Ниже показан целевой вариант REST API для задач. Фактические маршруты зависят
от текущей реализации роутера.

### Создать задачу

```http
POST /tasks
Content-Type: application/json
```

```json
{
  "title": "Подготовить README",
  "description": "Описать архитектуру Axum Task Service"
}
```

Пример успешного ответа:

```http
HTTP/1.1 201 Created
Content-Type: application/json
```

```json
{
  "id": 1,
  "title": "Подготовить README",
  "description": "Описать архитектуру Axum Task Service",
  "completed": false
}
```

### Получить список задач

```http
GET /tasks
```

Пример ответа:

```json
[
  {
    "id": 1,
    "title": "Подготовить README",
    "description": "Описать архитектуру Axum Task Service",
    "completed": false
  }
]
```

### Получить одну задачу

```http
GET /tasks/{id}
```

### Обновить задачу

```http
PATCH /tasks/{id}
Content-Type: application/json
```

```json
{
  "title": "Обновить README",
  "completed": true
}
```

### Удалить задачу

```http
DELETE /tasks/{id}
```

Ожидаемый ответ:

```http
HTTP/1.1 204 No Content
```

## Обработка ошибок

Ошибки приложения должны быть определены в `src/errors/` и централизованно
преобразованы в HTTP-ответы.

| Ситуация | HTTP-код | Пример |
|---|---:|---|
| Некорректные входные данные | `400 Bad Request` | Пустой заголовок задачи |
| Неавторизованный запрос | `401 Unauthorized` | Отсутствует или неверен токен |
| Доступ запрещён | `403 Forbidden` | Пользователь изменяет чужую задачу |
| Задача не найдена | `404 Not Found` | Запрошен несуществующий `id` |
| Конфликт данных | `409 Conflict` | Нарушено ограничение уникальности |
| Внутренняя ошибка | `500 Internal Server Error` | Ошибка PostgreSQL или сервера |

Пример JSON-ответа об ошибке:

```json
{
  "error": "Task not found"
}
```
